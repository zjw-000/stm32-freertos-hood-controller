## 三、白话教学已完成课程与掌握情况（按时间推进）

### 第一课：StartTask（开工准备员）
- **核心画面**：整个系统是个车间，`StartTask` 是一次性的开工准备员；其他任务是长期工作的员工；调度器是分配 CPU 的管理员。
- **已学概念**：
  - **临界区 (`taskENTER_CRITICAL` / `taskEXIT_CRITICAL`)**：一段不希望被其他任务中途打断的代码（先关门备料，备齐再放行）。
  - **一次性自删 (`vTaskDelete(NULL)`)**：开工准备员把长跑员工和定时器建好后，使命完成，退出并由 Idle 任务回收资源。
- **用户互动反馈与掌握情况**：
  - Q1: *为什么 StartTask 要等所有任务都创建完，再允许它们开始工作？*
    - 用户回答：**“避免系统只准备一半就开始工作”**（完全掌握临界区保护全局初始化的目的）。
  - Q2: *为什么 StartTask 完成创建工作后，要删除自己？*
    - 用户回答：**“它的准备工作已经全部完成”**（完全掌握动态一次性任务生命周期）。

### 第二课：KeyScanTask（按键值班员）
- **核心画面**：像一个每隔 10ms 巡视一次按键的值班员，根据动作打标记，由主逻辑读取后执行。
- **已学概念**：
  - **轮询**：每隔一段时间主动检查一次（`while(1)` 搭配 `delay_ms(10)` 让出 CPU 休眠）。
  - **消抖**：真实机械触点按下瞬间有弹跳，必须持续检测约 30ms 确认电平稳定，排除瞬间抖动误判。
  - **事件驱动与 ClearEvent**：`Key_Scan` 只留下“短按/长按/松开”的结果（事件），处理完毕后必须清空事件，防止下轮被重复处理。
  - **按键状态机**：空闲 → 等消抖 → 确认按下 → 根据按住时长分流为短按 / 长按。
  - **长按分流**：`LONG_PRESS`（达到 1s 阈值时只触发一次电机开关） vs `LONG_PRESSING`（持续按住时蜂鸣器持续叫，不反复切电机）。
- **用户互动反馈与掌握情况**：
  - Q3: *为什么每次检查按键后，要执行 delay_ms(10)？*
    - 用户回答：**“让其他任务也有机会运行”**（掌握 RTOS 阻塞延时让出 CPU 原理）。
  - Q4: *如果程序发现按键按下，但不到 30ms 就又松开了，应该怎样处理？*
    - 用户回答：**“不算，可能只是按键抖动”**（掌握消抖判据）。
  - Q5: *一个按键已经稳定按下，保持约 500ms 后松开，程序会把它判断成什么？*
    - 用户回答：**“短按”**（掌握短按判定区间）。
  - Q6: *处理完一次短按后，为什么要调用 ClearEvent()？*
    - 用户回答：**“避免一次短按被重复处理”**（掌握事件消耗机制）。
  - Q7: *为什么刚确认按键被按下时，程序还不能立即判断为短按？*
    - 用户回答：**“因为还不知道用户会马上松开还是继续长按”**（掌握状态机延迟决策）。
  - Q8: *按键2一直按住超过 1 秒时，电机开关动作应该触发几次？*
    - 用户回答：**“只触发一次”**（掌握单次边缘触发与持续电平状态的区别）。
- **源码回看（2026-09-03，进行中）**：
  - 用户反馈：面对完整 `key.c` 时仍看不懂具体代码，需要把已懂的机制映射回 C 语言字段和分支。
  - 本轮已拆解：`Key_t` 是每个按键的档案；`state` 表示判断过程所处阶段，`event` 表示输出给外界的结果；`pressStartTick` 保存计时起点；`readPin` 暂按“检查本按键的按钮”理解，不深入函数指针语法。
  - 已讲短按路径：`IDLE -> DEBOUNCE -> PRESSED -> 松手 -> SHORT_PRESS -> IDLE`。短按只能在松手时确认，因为刚按下时尚不知道用户会不会继续按成长按。
  - 已概览长按路径：超过 1 秒产生一次 `LONG_PRESS`，继续按住产生 `LONG_PRESSING`，松手产生 `RELEASE`；`longPressTriggered` 防止一次长按被当作短按。
  - **待互动确认**：用户能否区分“状态是判断过程”和“事件是最终结果”；未确认前不宣称已经能独立阅读状态机源码。

### 第三课：SensorTask（环境采集员，已闭环）
- **核心画面**：每隔约 500ms 采集一次 DHT11（温湿度）和 MQ2（燃气浓度），写到 `g_systemState` 这块公共白板上供系统其他模块查看。
- **已学概念**：
  - **互斥锁 (Mutex)**：公共白板的“卫生间门锁”。同一时刻只允许一个人进去写或读，写完立刻开锁（`xSemaphoreGive`）。
  - **采集周期与让出 CPU**：采集完成后休眠约 500ms，把 CPU 让给按键和电机等其他任务。
- **用户互动反馈与掌握情况**：
  - Q9: *SensorTask 修改 g_systemState 前，为什么要先取得互斥锁？*
    - 用户回答：**“防止多个任务同时读写公共数据造成混乱”**（完全掌握互斥锁保护共享资源、防数据撕裂的核心本质）。

### 第四课：MotorTask（动力执行员，进行中）
- **核心画面**：像机房里的“操作工”。每隔一段时间看一眼公共白板，看看当前是什么模式、按键设置了什么档位、传感器报了什么数值，然后去推电机的油门。
- **已学概念**：
  - **模式守卫**：开工前先看大开关。如果白板上写着 `MODE_OFF`（关机）或待机，二话不说立刻让电机停转（`motor_stop()`），防止空转浪费与安全隐患。
- **用户互动反馈与掌握情况**：
  - Q10: *在 MotorTask 中，如果看到工作模式是 MODE_OFF（关机），它第一步该干什么？*
    - 用户回答：**“当关机或待机时，立即把电机停下”**（完全掌握状态优先级的安全守卫逻辑）。

  - **自动模式直驱 (WindSpeed -> motor_pwm_set)**：根据 SensorTask 写在白板上的温湿度和燃气浓度，算出一个建议油门 `auto_pwm`，直接给到电机，不需要复杂闭环。
  - **计算与执行分离（源码核对）**：`WindSpeedTask` 每 100 ms 调用 `WindSpeed_Update(temp, humidity, gas)`，执行归一化、加权融合和 PWM 计算，并把结果缓存到模块内部的 `g_windSpeedData.pwmValue`；`MotorControlTask` 的 `AUTO_STATE_COOKING` 分支不重复计算公式，只调用 `WindSpeed_GetPWMCompare(MAXCCR)` 读取缓存结果、换算成 CCR，再交给 `motor_pwm_set()`。这是“生产者计算，消费者取结果”的跨任务流水线。
  - **命名辨析**：本项目所谓“风速算法”并未测量或闭环控制真实风量；从源码看，它实际是“环境传感器数据 -> 建议 PWM”的前馈映射算法。
- **用户互动反馈与掌握情况**：
  - Q11: *在自动模式（MODE_AUTO）下，系统是怎么决定风机油门（PWM）大小的？*
    - 用户回答：**“根据传感器测到的油烟/燃气/温度计算出油门大小，直接控制电机出力”**（完全掌握自动模式的传感器输入到油门直接输出映射机制）。

- **关键高价值认知突破（2026-09-03）**：
  - 用户提问：*“闭环调节为什么不属于自动模式，而算法计算定值才属于自动模式？”*
  - 白话释疑：
    1. **MODE_AUTO（自动替人做决定）**：看环境脸色，油烟大直接给大油门（直驱），核心在于宏观排烟策略。
    2. **MODE_MANUAL 闭环（替人死磕执行指标）**：人定死挡位（如2000 RPM），系统通过编码器测速+PID进行定速巡航（阻力大多给油，阻力小少给油）。
  - 用户确认：完全理解两者的分工与定位。

### 第五课：PID 定速巡航三兄弟（进行中）
- **核心画面**：泡洗澡水/踩油门调节器。三兄弟分工合作把转速稳在目标值。
  1. **大哥 P（比例）**：盯眼前。误差大就猛踩，误差小就轻踩。
  2. **二哥 I（积分）**：纠执念/翻账本。消除长期卡在目标附近的顽固残差。
  3. **三哥 D（微分）**：踩刹车。看冲刺速度，防止冲过头超调。
- **已学概念**：
  - **P项（比例项）**：`output_p = Kp * error`。当前差距有多大，出力就按比例给多大。
- **用户互动反馈与掌握情况**：
  - Q12: *当电机实际转速和目标转速差距很大时，大哥 P（比例项）主要负责干什么？*
    - 用户回答：**“立刻根据当前误差的大小，按比例猛踩或收松油门（差距大就大出力）”**（完全掌握比例项的实时动态响应机制）。
  - **I项（积分项）**：`output_i = Ki * error_sum`。专门消灭静态误差（静差）。
- **用户互动反馈与掌握情况**：
  - Q13: *当风机转速卡在 1980 转（离目标 2000 转只差一点点，P大哥推不动了）时，二哥 I 是怎么把这剩下的差距抹平的？*
    - 用户回答：**“只要转速还没完全达到目标，他就把微小的差距按时间不断累加，提供持续增加的推力抹平残差”**（完全掌握积分消除静差的核心机制）。
  - **D项（微分项）**：`output_d = Kd * (error - prev_error)`。观察误差变化趋势，提供阻尼，抑制超调和震荡。
  - Q14: *在定速巡航中，三哥 D（微分项）最核心的使命是什么？*
    - 用户回答：**“监测转速往上冲的猛烈程度，提前施加反向刹车，防止电机转速冲过头（超调）和震荡”**（完全掌握微分项根据变化趋势抑制超调的核心作用）。
  - **项目真实实现核对**：位置式 PID 参数为 `Kp=14.0`、`Ki=1.65`、`Kd=0.0`，输出限幅为 `0~1000`；因此当前实际运行的是 PI 控制，D 项代码保留但未启用。`MotorTask` 每 50ms 计算一次，低/高挡目标分别为 190/220 RPM，输出直接成为 TIM1 的 CCR（约对应 0%~100% 占空比）。
  - Q15: *高挡目标 220 RPM、实际 180 RPM时，这一轮 PI 输出如何传到电机？*
    - 用户回答：**“误差为40，P和I合成得到626，CCR1约为626，对应约62.6%占空比”**（已能串联目标/实际转速、误差、PI合成、CCR与PWM占空比）。
  - Q16: *第二轮实际转速升到 210 RPM 后，PI 输出为何从 626 降到约 222.5？*
    - 用户回答：**“因为实际转速已接近目标，当前误差从40缩小到10，P出力明显变小；I保留历史账本，最终油门降到约22.2%”**（已掌握 P 随当前误差收小、I 保留历史累计，以及 PI 每 50ms 连续重算的关系）。
- **阶段结论**：P、I、D 三项职责及项目实际 PI 参数均已掌握；已完成连续两轮计算，当前进入“误差为零时为何仍需维持油门”。

## 第六课（特辑）：FreeRTOS + STM32 启动全流程白话拆解（开启）
- **教学目标**：彻底理解从芯片上电复位 -> Reset_Handler -> main() -> 任务创建(TCB/栈) -> vTaskStartScheduler()触发SVC -> 永不返回的首任务运行。

- **第一幕：通电到进入 main()（已掌握）**：
  - 芯片从 0x08000000 拿初始 SP，从 0x08000004 拿 PC 跳入 Reset_Handler。
  - SystemInit 调好系统时钟。
  - 运行 C 库 `__main`：搬运 data 段到 SRAM，擦除清零 BSS 段。
  - 最后跳转至用户写的 `main()`。
  - Q14: *从芯片通电复位，到真正进入我们写的 main() 函数，中间经历的“打扫与准备”过程是什么？*
    - 用户回答：**“先由芯片底层完成时钟启动、数据搬运与内存清零，打扫好环境后再跳入我们写的 main()”**（完全掌握）。


  - **用户高价值延伸提问（TaskHandle_t 句柄到底是什么）**：
    - 用户发问：*“(TaskHandle_t* )&StartTask_Handler // 工牌挂绳指针（TCB句柄）这个参量是什么意思？”*
    - 白话释疑：TCB 是抽屉里的个人档案卡，Handle（句柄）就是系在工牌上的细绳/挂绳（即指针）。外面的人如果想控制这个演员（比如删除、挂起、唤醒），不需要翻箱倒柜找大结构体，只要拽着这根绳子（Handle 指针）就能精准下令。


  - **第二幕：main() 内创建任务与句柄作用（已掌握）**：
    - 创建任务三件事：分配工牌（TCB）、发私人笔记本（任务栈 Stack）、挂入等候名单（就绪表 Ready List）。
    - 任务句柄 Handle：系在 TCB 档案卡上的“提线木偶挂绳”（TCB 结构体指针），供外部代码随时删除 (vTaskDelete)、挂起 (vTaskSuspend) 或通知该任务。
    - Q15: *在 FreeRTOS 创建任务时，传入 (TaskHandle_t*)&StartTask_Handler 这个参数的核心用途是什么？*
      - 用户回答：**“它是一个把手/指针（指向该任务的TCB档案卡），系统赋值后，方便我们后续凭它来删除、挂起或控制该任务”**（精准吃透）。


  - **第三幕：vTaskStartScheduler 调度器开幕与永不返回（已完全掌握）**：
    - 三件法宝大白话：
      1. **SVC 异常（开幕锣鼓）**：只用一次，触发 CPU 换上第一个任务的笔记本（任务栈）并跳转执行。
      2. **SysTick 滴答定时器（节拍器）**：1ms 一次心跳，驱动任务延时与时间片轮转。
      3. **PendSV 异常（换人幕布）**：执行实质性的任务上下文切换（保存旧任务栈、恢复新任务栈）。
    - 永不返回真相：CPU 控制权彻底移交多任务调度器，各任务在抢占/时间片机制下轮番登上 CPU 舞台，再也无需退回到 main()。
    - Q16: *为什么在 FreeRTOS 的 main() 函数末尾，vTaskStartScheduler() 函数被称为“永不返回”？*
      - 用户回答：**“它触发了SVC开幕锣，让CPU直接跳入第一个任务中运行，从此CPU只在任务间轮流切换，再也不会退回main()函数”**（彻底吃透全流程！）。

- **拆解规划**：
  1. 第一幕：通电到进入 main()（硬件拉手、清零搬家）。
  2. 第二幕：main() 里的准备工作（招募演员、发工牌TCB与笔记本栈）。
  3. 第三幕：调度器开幕演出（SysTick、PendSV、SVC交接仪式与永不返回）。
- **当前进度**：讲授第一幕。

## 第八课：二值信号量（Binary Semaphore）与中断同步（开启）

- **计数信号量核验**：`FreeRTOSConfig.h:115` 的 `configUSE_COUNTING_SEMAPHORES` 配置为 `1`，只表示内核编译支持计数信号量。业务源码中未找到 `xSemaphoreCreateCounting`、`xSemaphoreCreateCountingStatic` 或 `xQueueCreateCountingSemaphore` 的调用，因此没有实际创建计数信号量。

- **概念边界**：互斥量用于保护共享数据；二值信号量用于“事件到了”的同步；计数信号量才用于累计多个同类资源或多个未消费事件。当前测速通知使用二值信号量，连续多次通知可能合并，不具备计数信号量的累计能力。
- **源码核验（硬件中断与二值信号量）**：
  - 已启用测速链：`System_Init()` 创建 `g_speedCalcSemaphore`；`SpeedCalcTask` 在 `xSemaphoreTake(..., portMAX_DELAY)` 阻塞等待；`TIM4_IRQHandler` 只清更新标志、`xSemaphoreGiveFromISR` 通知并按需 `portYIELD_FROM_ISR`，速度读取和 `get_speed()` 计算在任务中执行。

## 第九课：FreeRTOS 临界区与中断屏蔽（进行中）
- **用户疑问**：*“临界区的代码是怎么实现的配置和屏蔽的？我有点混乱。”*
- **项目源码实证**：
  1. `FreeRTOSConfig.h` 配置 `configPRIO_BITS = 4`、`configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 3`，因此写入硬件的门槛值是 `configMAX_SYSCALL_INTERRUPT_PRIORITY = 0x30`。
  2. 任务中调用链：`taskENTER_CRITICAL()` → `portENTER_CRITICAL()` → `vPortEnterCritical()` → `vPortRaiseBASEPRI()` → `msr BASEPRI, 0x30`。
  3. 效果：暂时屏蔽逻辑优先级 3～15 的可屏蔽中断；0～2 级高紧急中断以及 NMI、HardFault 不受这道 `BASEPRI` 门槛影响。
  4. 因 SysTick 和 PendSV 被设成最低优先级，它们也会被挡住，所以临界区内不会发生 FreeRTOS 任务切换。
  5. `uxCriticalNesting` 记录嵌套层数；每次退出减一，只有回到 0 才执行 `BASEPRI = 0`，避免内层退出时错误地提前解除外层保护。
  6. ISR 中不能使用普通任务版宏，应使用 `taskENTER_CRITICAL_FROM_ISR()` 保存旧 `BASEPRI`，再用 `taskEXIT_CRITICAL_FROM_ISR(saved)` 恢复旧值。
- **项目调用点**：`StartTask()` 用临界区包住其他任务的创建和 `TIM4_init()`，直到初始化完成才允许正常调度。
- **待确认概念**：区分“编译期配置门禁阈值”“运行时写 BASEPRI 关门”“退出时按嵌套层数恢复”三件事。

## 第十课：整机事件流总图（正在讲授，待互动确认）

- **用户当前困难**：局部学过任务、定时器、中断和临界区，但无法把初始化、正常运行、任务切换和中断插队串成同一条时间线。
- **统一核心画面**：STM32 只有一个 CPU 舞台；任务是会工作、会睡眠的员工，FreeRTOS 调度器挑选最高优先级的就绪任务；硬件定时器各自计时，中断只做紧急通知，复杂工作交还任务。
- **源码核验出的启动链**：
  1. `main()` 先执行 `Hardware_Init()`；此时调度器未启动，显示后的 `delay_ms(500)` 是原地等待。
  2. `System_Init()` 初始化公共状态，并创建数据互斥量和测速二值信号量。
  3. 只创建 `StartTask` 后启动调度器；`StartTask` 在临界区中创建长期任务并最后启动 TIM4，退出临界区后自删除。
- **用户追问：启动延迟的体感**：
  - 用户询问 FreeRTOS 烟机启动是否基本感觉不到延迟。
  - 已澄清：FreeRTOS 启动调度器本身通常不是明显体感来源；本项目却主动显示 `Init Complete!` 后忙等约 500 ms，因此从通电到长期任务运行会有可察觉但通常可接受的半秒级开机过程。
  - 运行后各交互节拍不同：按键任务每 10 ms 扫描且需至少 30 ms 消抖；电机任务周期约 50 ms；UI 最多还需等待约一个 200 ms 刷新周期；自动感应链还受 500 ms 传感器采集和 100 ms 风速决策周期影响。
  - 边界：硬件初始化本身还会耗时，且以上均为源码设计周期，尚未经过上板测量，不能宣称精确端到端延迟。
- **四类节拍/计数器的分工**：
  1. SysTick 每 1 ms 给 FreeRTOS 记账，管理任务延时、时间片和调度时机。
  2. TIM1 独立输出约 1 kHz PWM；CPU 只需偶尔改 CCR，硬件会持续产生高低电平。
  3. TIM2 用编码器模式持续累计电机脉冲；通常无需每个脉冲都进入中断，更新溢出时才进入 `TIM2_IRQHandler()`。
  4. TIM4 每 1 ms 中断一次，只向测速二值信号量“按门铃”；`SpeedCalcTask` 被唤醒后读取 TIM2 计数并计算转速。
- **任务切换的三种主要原因**：当前任务 `delay_ms()`/等待信号量而阻塞；更高优先级任务变为就绪而抢占；同优先级就绪任务由 1 ms tick 做时间片轮转。
- **测速链的精确边界**：`SpeedCalcTask` 优先级 6；TIM4 ISR 发信号后可立即触发调度。`get_speed(..., 50)` 首次在第 51 次有效唤醒形成样本，之后约每 50 次形成一个样本；累计 10 个样本后才更新滤波转速，首次约需 501 次有效唤醒。二值信号量若来不及消费会合并通知，因此这是源码设计节拍，不是未经测量的绝对实时时间保证。
- **一次正常运行的主循环画面**：按键任务改状态，传感器任务写环境数据，风速任务算自动模式建议值，电机任务按模式执行停机/PID/自动直驱，UI 显示快照，防回流任务检查燃气状态；它们大部分时间在延时，CPU 在就绪任务间快速切换。期间 TIM1/TIM2 自主运行，SysTick/TIM4 短暂插队。

- **用户问题（读取总计数与方向）**：用户询问`get_encoder_value()`和`TIM_GetDirection()`。讲授模型：TIM2的16位CNT是只能显示0~65535的“小里程表”，`overflow`是软件扩展高位；总计数=`CNT + overflow*65536`。向上跨过65535时CNT回0且overflow++；向下跨过0时CNT回65535且overflow--。`TIMx->CR1 & TIM_CR1_DIR`只取CR1中的DIR位，置1表示向下计数、清0表示向上计数，三目运算转成1/0；编码器模式下该位由A/B相序驱动并只读。TIM2 ISR据此决定overflow减一或加一。

- **用户追问（overflow是否STM32标签）**：不是。源码在`USER/main.h`由作者定义`volatile int overflow=0;`，在`motor.h`以`extern volatile int overflow;`声明。变量名可改为其他合法名称；它之所以表示跨界次数，是TIM2更新中断在向上/向下跨界时显式执行`overflow++/--`。STM32硬件只提供CNT跨界产生的更新事件/中断及CR1.DIR方向位，软件变量负责记忆历史次数。`volatile`表示该值可能被中断异步修改，提醒编译器每次从内存读取，不是“溢出计数”语义。

### SensorTask采集与发布链路（2026-09-07，待互动确认）
- **任务职责**：`SensorTask()`只负责定期采集DHT11温湿度和MQ2气体数据，再发布到共享的`g_systemState`；它不直接计算目标风速或控制电机。后续`WindSpeedTask()`读取快照并计算风速，`MotorControlTask()`再按模式执行。
- **DHT11路径**：`DHT_Read_Data(&temp,&humi,...)`通过指针输出两个`u8`值，驱动读取5字节并比较`BUF[4]`与前4字节之和；返回1才把局部`temp/humi`写入共享状态。返回0时保留共享状态里的上一次有效数据。
- **MQ2路径**：`MQ2_GetGasConcentration()`连续读取10次ADC并取平均，再由电压、电阻公式换算成`float`浓度；该接口没有独立成功标志，任务每轮都直接发布结果。
- **互斥量边界**：源码实际只有同一个`g_dataMutex`，不是注释所称“两把锁”；正确含义是分两次短暂获取同一把锁。耗时的DHT时序和MQ2采样均在锁外执行，锁内只复制少量共享字段，缩短其他任务等待时间。`portMAX_DELAY`表示锁暂时被占用时一直阻塞等待，成功取得后才写入并及时释放。
- **本轮注释辨析**：`SensorTask()`中的“采用两把锁”不准确；代码只创建了一把`g_dataMutex`（`xSemaphoreCreateMutex()`），只是对DHT结果和MQ2结果分别执行一次`Take/Give`，形成两个短临界区。若从DHT采集开始一直持锁到MQ2采集结束，锁会被占用更久，其他任务访问`g_systemState`需要等待；这会增加阻塞时间，但不等于必然发生优先级反转。优先级反转的典型链路是低优先级任务持锁、高优先级任务等待、中优先级任务反复抢占低优先级任务；FreeRTOS互斥量可用优先级继承缓解，但不能让长临界区变短。
- **白话模型**：传感器采集像在房间外测量，不能让测量过程占着公共档案柜；测完后只拿钥匙很短时间，把结果写进档案再归还。DHT的温度/湿度作为一组一起发布，MQ2结果单独发布；两次发布之间允许其他任务短暂读取旧的或上一批气体数据，这是当前设计的取舍。
- **建议改正注释**：可写成“传感器采集耗时，不能在采集期间长期持有`g_dataMutex`；因此在采集完成后分两次短暂获取同一把锁，分别发布DHT和MQ2结果”，不要写“采用两把锁”。
- **代码风险**：若开启`SENSOR_DEBUG`且首次DHT校验失败，局部`temp/humi`尚未初始化却会被`printf`读取，打印值不可靠；应初始化变量、失败时打印错误或只在成功时打印。MQ2换算中`tmep`接近0还存在除零/极大值风险，当前驱动未见显式防护。
- **下一互动锚点**：让用户判断DHT校验失败后，共享状态应保留上次有效温湿度，还是写入本次未可靠的数据；并确认互斥锁保护的是共享数据复制，不是整个传感器采集过程。

### MotorControlTask共享状态同步（2026-09-07，待互动确认）
- **先纠正问题**：多个任务只读同一变量通常不冲突；危险主要来自读写或写写并发。`MotorControlTask()`并非只读，它也会更新`motorRunning`、`targetRPM`、计数器和模式等字段。
- **当前代码事实**：该任务只在把全局`speed`复制到`g_systemState.actualRPM`时取得`g_dataMutex`，随后对`currentMode`、`speedLevel`、`motorRunning`、`cookingEventActive`等访问均未显式持锁；因此不能概括为“读取共享状态不需要锁”。
- **为何眼下多半能运行**：工程启用抢占调度；电机任务优先级5，高于按键4、传感器/风速3、防回流2和UI1。它在每轮开头取得并释放互斥锁后，只要不阻塞，遵守该锁的低优先级写者通常不能插入本轮控制分支。这是依赖优先级和代码不阻塞的隐含时序，不是互斥保证，改优先级或加入阻塞调用后会失效。
- **明确例外与风险**：`AntiBackflowTask()`裸写`antiBackflowActive`、`motorRunning`、`gasThreshold`；`UIDisplayTask()`也裸读多个字段。更高优先级`SpeedCalcTask`会更新`volatile float speed`，可在电机任务中途抢占，使本轮写入`actualRPM`和PID计算读取到不同批次速度。单个对齐标量在Cortex-M3上通常不会被撕成半个值，但不保证多个字段是同一时刻的组合，也不等同于完整线程安全。
- **推荐边界**：电机任务每轮先在锁内一次复制决策所需字段到局部快照，立即解锁，PID和硬件控制在锁外做；需要发布的多个状态先在局部计算，再短暂加锁成组写回。所有其他任务访问同一批共享字段也必须遵守同一同步规则。不要在锁内调用可能耗时或阻塞的LCD、传感器和电机操作。
- **下一互动锚点**：让用户判断“UI和Motor同时只读`currentMode`”与“Key写`currentMode`时Motor读取”哪一种需要同步，并说明锁保护的是读写过程/状态组合，不是因为变量名字属于结构体。

- **旧互动锚点保留**：只让用户判断两个例子：65535向上再来一脉冲为何总数是65536；0向下再来一脉冲为何总数是-1。

## 第八课：IAP 固件升级（进行中）
- **核心流程**：上位机串口发送固件，DMA搬入 `receive_buff`；DMA完成中断释放 `g_iapSemaphore`，唤醒 `iap_task`。
- **已掌握**：用户确认 DMA 收到数据后不能直接写 Flash，必须先用 `CRC32_VerifyFirmware()` 检查固件完整性；校验数据格式为“固件数据 + 4字节 CRC32”。
- **源码结论**：校验通过后 `firmwareLen = receivedLength - 4`，先检查 APP 地址，再擦除 `FLASH_APP1_ADDR`，只把固件本体写入 APP 区，随后检查 APP 复位向量并调用 `iap_load_app()`。
- **当前进度**：正在讲解 Flash 擦除、写入与 APP 跳转的区别。

## 第九课：SensorTask 与 WindSpeedTask 周期关系（进行中）
- **用户已识别**：`SensorTask` 约 500 ms 更新一次环境数据，而 `WindSpeedTask` 每 100 ms 对同一批数据计算，期间多数计算重复。
- **关键澄清**：示例中的 `320 ms` 是相对系统启动时刻的任意绝对时间，用来表示任务相位，不是 `SensorTask` 周期内的固定更新时间。
- **源码边界**：采集与共享状态更新发生在 `delay_ms(500)` 之前；调度器运行后该延时调用 `vTaskDelay()`，所以相邻采集时刻约为“本轮采集执行时间 + 500 ms”，并非严格固定 500 ms。严格周期应考虑 `vTaskDelayUntil()`，更合适的任务协作可由采集完成后通知计算任务。

## 第十课：KeyScanTask 与 MotorControlTask 周期设计（进行中）
- **按键周期**：`KeyScanTask` 每约 10 ms 调用 `Key_Scan()`，配合 30 ms 消抖和 1000 ms 长按阈值；快速扫描主要用于避免漏掉较短按压并降低按下/释放识别延迟。
- **电机周期**：TIM4 每 50 ms通过二值信号量触发 `SpeedCalcTask`，后者按 50 ms 测速窗口更新 `speed`；`MotorControlTask` 每约 50 ms执行一次 PID、PWM更新和自动模式状态检查，设计意图是控制周期与反馈更新周期匹配。
- **源码边界**：`MotorControlTask` 没有直接等待测速完成通知，只用独立的 `delay_ms(50)`，因此两个同周期任务可能存在相位差，偶尔使用上一帧转速；状态机直接用 `counter += 50` 也把实际调度时间近似当成严格 50 ms。PID实现未显式乘除采样时间，参数与50 ms调用周期绑定。

## 第十一课：烟机任务的物理场景总图（进行中）
- **讲解主线**：以“用户按键、开始炒菜、油烟增强、自动排烟、停止炒菜后的延时排烟、防回流”串联任务，而非孤立解释函数。
- **物理闭环**：`KeyScanTask` 输入用户意图；`SensorTask` 采集环境；`WindSpeedTask` 将环境量映射成自动PWM需求和Cooking Event；`MotorControlTask` 输出电机使能/PWM并运行自动状态机；编码器 + TIM4 + `SpeedCalcTask` 产生实际RPM反馈，供手动/防回流模式PID闭环使用；`UIDisplayTask` 显示系统快照，`AntiBackflowTask` 处理非烹饪场景气体倒灌。
- **应明确的工程边界**：本项目把DHT11温湿度和MQ2气体浓度作为油烟程度的间接代理，并没有直接检测气流或真实油烟颗粒；自动模式为规则+权重映射，非严格物理风量控制。
