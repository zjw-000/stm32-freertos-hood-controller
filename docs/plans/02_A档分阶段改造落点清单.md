# 02_A档分阶段改造落点清单

> **范围**：保住现有 BOM（STM32F103C8T6 + W25Q64 + USART1），只改软件。
> **落点**：2 个 Keil 工程（`Bootloader/bootloader.uvprojx`、`USER/project.uvprojx`）+ 2 个上位机 Python 工具。
> **基线实测**（改造前）：Bootloader `ER_IROM1 Size = 0x00000BDC`（≈2.97KB / 上限 8KB，**余量 ≈5KB**）；`tools/APP.bin` = 3688 字节（正好卡在 4KB 接收缓冲内）。

---

## 0. 分区与容量基线（改造前，务必先对齐）

| 区域 | 地址 | 大小 | 备注 |
|---|---|---|---|
| Bootloader | `0x08000000 ~ 0x08001FFF` | 8 KB | 实测用 2.97KB |
| APP | `0x08002000 ~ 0x0800FFFF` | 56 KB | `MCU_APP_ADDR` |
| W25Q64 META | `0x000000` | 4 KB | `SPI_META_ADDR`，单份 |
| W25Q64 DOWNLOAD | `0x001000` | 60 KB | `SPI_DOWNLOAD_ADDR` |
| W25Q64 BACKUP | `0x010000` | 64 KB | `SPI_BACKUP_ADDR` |
| W25Q64 GOLDEN | `0x020000` | 64 KB | `SPI_GOLDEN_ADDR`，**定义但零引用** |

## P0 修复阶段 —— 不修则无法联调（0 新功能）

### 1. `USER/system_stm32f10x.c`
- **`VECT_TAB_OFFSET`（L128）**：当前 `0x0`，且 `SystemInit()`（L264-268）用 `SCB->VTOR = FLASH_BASE | VECT_TAB_OFFSET` 写 VTOR。
  - 后果：**APP 运行在 0x08002000，但 VTOR 指向 0x08000000（Bootloader 的向量表）**，APP 的 TIM4/DMA/USART1/TIM2 中断全部落到 Bootloader 的 weak `Default_Handler`。
  - 改动：把 L128 的宏改成 `#ifndef VECT_TAB_OFFSET` 包裹，默认 `0x0`（Bootloader 工程不加宏，保持正确）。
- **注意**：`bootloader.uvprojx` 与 `project.uvprojx` **引用的是同一份** `USER/system_stm32f10x.c`，所以不能直接改宏值，否则 Bootloader 也被改成 0x2000。

### 2. `USER/project.uvprojx`
- **C/C++ → Define**：追加 `VECT_TAB_OFFSET=0x2000`（当前仅 `STM32F10X_MD,USE_STDPERIPH_DRIVER`）。
- `bootloader.uvprojx` **不加**该宏。

### 3. `USER/main.c`
- **`main()`**：可选加固——在 `Hardware_Init()` 之前显式 `SCB->VTOR = FLASH_BASE | 0x2000;` 作为双保险。
- **`Hardware_Init()` / `main()`**：`App_Confirm_Healthy()` 目前**只有定义（`app_tasks.c:1317`）和 extern 声明（`main.c:1`），零调用点**。
  - 后果：升级后 `ota_state` 永远停在 `TESTING`，`boot_retry_cnt` 每次开机 +1，**第 4 次开机触发回滚**，好固件被自动换回旧固件。
  - 改动：在系统自检通过后调用一次（建议放在 `StartTask` 完成 LCD/传感器自检之后，而非 `main()` 里）。

### 4. `APP_TASK/app_tasks.c`
- **`App_Confirm_Healthy()`（L1317）**：逻辑本身可用，改为调用共享的 `BootMeta_Write()`（见 P2），并加写后回读校验。
- **`StartTask()`**：新增"自检通过 → `App_Confirm_Healthy()`"调用点。

### 5. `SYSTEM/usart/usart.c`
- **`USART1_IRQHandler()`（L92）**：IDLE 中断**无条件**触发升级路径（`DMA_Cmd(DISABLE)` + 给信号量），任意串口帧（哪怕一个字节）都会唤醒 `iap_task`。
  - 改动：加"升级会话"门控——只有收到合法 `BEGIN` 帧后才置 `g_upgradeActive = 1`，非会话期走普通串口逻辑。

**验收**：APP 中断正常（TIM4 1ms 节拍、编码器测速、电机 PID 工作），升级一次后重启不回滚。

## P1 传输层 —— 分片流式下载（解 4KB 上限）

### 6. `Shared/boot_config.h`
- 新增协议常量：`IAP_FRAME_MAGIC`、`IAP_BLOCK_SIZE (4096)`、`IAP_CMD_BEGIN/DATA/END`、`IAP_RX_TIMEOUT_MS`。
- 新增结构：`IapFrameHeader_t { cmd, seq, offset, len, crc32 }`、`IapManifest_t { magic, total_len, total_crc32, ver_major, ver_minor, block_count }`。
- 新增 `#define IAP_MAX_FW_SIZE (56*1024)` 与静态断言（`total_len <= IAP_MAX_FW_SIZE`）。

### 7. `SYSTEM/sys/sys.h`
- **`buff_size`（L51）**：`4096` 保留，但**语义从"整包缓冲"改为"单块缓冲"**，不再决定固件上限。
- `receive_buff` 仍在 `0x20004000`（RAM 顶部，`0x20004000~0x20005000`），无需挪动。

### 8. `APP_TASK/app_tasks.c`
- **`iap_task()`（L1334）**：核心重写为状态机，只做分发：
  - 新增 `static void Iap_HandleBegin(void)`：解析 manifest → 校验 `total_len ≤ 56KB` → `W25QXX_Erase_Range(SPI_DOWNLOAD_ADDR, total_len)` → `g_rxOffset = 0`。
  - 新增 `static void Iap_HandleData(void)`：校验 `header.offset == g_rxOffset` 且 `CRC32(block)` 正确 → `W25QXX_Write(receive_buff, SPI_DOWNLOAD_ADDR + offset, len)` → `g_rxOffset += len` → `MYDMA_Enable(DMA1_Channel5)` 收下一块。**每块即落盘**，掉电只丢当前块。
  - 新增 `static void Iap_HandleEnd(void)`：`g_rxOffset == total_len` 且总 CRC 通过 → 写 meta（`PENDING_APPLY`）→ `NVIC_SystemReset()`。
  - 异常分支：块 CRC 错 / `offset` 跳变 / `IAP_RX_TIMEOUT_MS` 内无新块 → 回 `BEGIN` 等待重传。
  - 删除 L1373 的"整包 `CRC32_VerifyFirmware`"与 L1422 的"整包 `W25QXX_Write`"。
- `W25QXX_Write` 的 `NumByteToWrite` 是 `uint16_t`，单块 4096 安全。

### 9. `BSP/DMA/dma.c`
- **`GetReceivedDataLength()`（L59）**：当前在任务上下文直接读 `DMA_GetCurrDataCounter(DMA1_Channel5)`。
  - 改动：在 `USART1_IRQHandler` 里把 CNDTR 快照存全局（DMA 已 DISABLE 时读），任务侧读快照，避免竞态。
- **`MYDMA_Enable()`（L50）**：保持"重装计数器 + 重新使能"，作为块间握手。

### 10. `SYSTEM/usart/usart.c`
- **`USART1_IRQHandler()`**：IDLE 分支增加"记录本次 IDLE 时刻（`xTaskGetTickCountFromISR`）"，供 `iap_task` 判定帧间超时。

### 11. `tools/send_firmware.py`（重写）
- 不再 `ser.write(整包)`，改为按 `IAP_BLOCK_SIZE` 分片，每片前加帧头（cmd/seq/offset/len/crc32）。
- 新增 `--block`、`--begin/--data/--end` 模式；片间等待 ACK 或固定延时（与固件侧超时匹配）。

### 12. `tools/add_crc32.py`（扩展为 `pack_firmware.py`）
- 保留末尾 4 字节 CRC32 兼容格式；**新增输出 manifest**（total_len / total_crc32 / version / block_count）。
- 可选：生成加密/签名镜像（P3）。

**验收**：发送 >4KB（如 20KB）固件完整升级成功；中途断电重启后重发仍能成功。

## P2 元数据掉电原子性 —— 双份 + 序号 + CRC

### 13. `Shared/boot_config.h`
- `BootMeta_t` 增加 `uint32_t meta_seq;`、`uint32_t meta_crc;`（自身校验）。
- 分区调整：`SPI_META_ADDR` 区扩为 2 个扇区（`0x000000` 槽A / `0x00001000` 槽B），**`SPI_DOWNLOAD_ADDR` 顺延到 `0x00002000`**。
  - ⚠️ 该地址变更必须**同步改三处**：`boot_config.h`、Bootloader 引用、上位机工具。
- 新增 `#define SPI_META_SLOT_A 0x00000000` / `SPI_META_SLOT_B 0x00001000`。

### 14. 新建 `Shared/boot_meta.c` / `boot_meta.h`（两工程都加入编译）
- `uint8_t BootMeta_Read(BootMeta_t *out)`：读 A/B 两槽，各校验 `magic` + `meta_crc`，取 `meta_seq` 大且 CRC 正确者；两槽皆坏 → 返回 0。
- `uint8_t BootMeta_Write(BootMeta_t *meta)`：`meta_seq = 上次序号+1`；算 `meta_crc`；**交替写另一槽**（擦 → 写 → 回读校验）。
- 目的：消除 `Bootloader/main.c` 的 `Read_Meta/Write_Meta` 与 `app_tasks.c:1436-1437` 的**两份重复实现漂移**。

### 15. `Bootloader/main.c`
- **`Read_Meta()`（L22）**：替换为 `BootMeta_Read()`。
- **`Write_Meta()`（L28）**：替换为 `BootMeta_Write()`。
- **`main()`（L101）**：保持状态机骨架（`PENDING_APPLY` → 备份 → 搬运 → `TESTING`；`TESTING` 且 `boot_retry_cnt>=3` → 回滚），仅把 meta 读写换成共享实现。

### 16. `APP_TASK/app_tasks.c`
- **`iap_task()`（L1428-1437）**：删除手写的 `W25QXX_Erase_Sector + W25QXX_Write`，改调 `BootMeta_Write()`。
- **`App_Confirm_Healthy()`（L1317）**：同上。

**验收**：写 meta 过程中拔电，重启后能唯一确定状态（旧态或新态，绝无"半写"）。

## P3 验签 / 镜像加密（量产建议，可选）

### 17. 新建 `Shared/verify.c` / `verify.h`
- `uint8_t Image_Verify(const IapManifest_t *mf, uint32_t fw_len)`。
- **算法选型受 8KB 约束**：Bootloader 余量约 5KB，Ed25519 验签代码通常 6~8KB → **放不进 BL**；AES-CMAC 约 1~2KB → 可放进 BL。

### 18. 决策点（二选一）
- **方案 B（推荐）**：**验签放 APP 侧**——`iap_task` 收完 `END` 后先 `Image_Verify`，通过才写 `PENDING_APPLY`。BL 保持极简。
- 方案 A：BL 扩到 16KB，APP 起点改 `0x08004000`。需同步改 `MCU_APP_ADDR`、`VECT_TAB_OFFSET`、APP 工程 IROM1 起点、上位机工具。**风险面大，不推荐**。

### 19. `APP_TASK/app_tasks.c`
- **`Iap_HandleEnd()`**：`if (!Image_Verify(...)) { LCD 报错; return; }` 再写 meta。

### 20. 新建 `tools/sign_firmware.py`
- 私钥签名，产出签名块并拼入镜像尾部。

## P4 看门狗与超时

### 21. `Bootloader/main.c`
- 新增 `static void IWDG_Init(void)`：`IWDG_WriteAccessCmd(Enable)` → `IWDG_SetPrescaler(64)` → `IWDG_SetReload(2500)` → `IWDG_ReloadCounter()` → `IWDG_Enable()`（40kHz/64 → 约 4s）。
- **`Backup_Current_App()`（L35）/ `Flash_App_From_SPI()`（L50）**：循环内每搬一块 `IWDG_ReloadCounter()`。
- ⚠️ **STM32F1 的 IWDG 一旦开启无法关闭**：`Jump_To_App()`（L81）跳转后 **APP 必须接管喂狗**，否则 4s 后被复位。

### 22. 新建 `BSP/IWDG/iwdg.c` / `iwdg.h`（APP 侧）
- `IWDG_Init()` / `IWDG_Feed()`。
- 新增最低优先级 `WatchdogTask`：各任务上报心跳位，**心跳位齐全才喂狗** → 实现"任务卡死也能复位"。

### 23. `Bootloader/main.c`
- **`Flash_App_From_SPI()`（L50）**：加总超时计数（循环上限），超限放弃并走回滚分支。

**验收**：升级中制造卡死（如断 SPI），IWDG 在 4s 内复位并回到可用状态。

## P5 刷后回读校验 + `backup_len` 语义修正

### 24. `Bootloader/main.c`
- **`Flash_App_From_SPI()`（L50）**：写完**从 `MCU_APP_ADDR` 回读算 CRC32**，与 `meta.firmware_crc32` 比对；不符 → **不置 `TESTING`**，直接走回滚。当前**完全无回读校验**。
- **`Bootloader/bootloader.uvprojx`**：把 `BSP/CRC32/crc32.c` 加入 BL 编译（当前只在 APP 工程）。
- **`Backup_Current_App()`（L35）**：当前固定备份 `MCU_APP_MAX_SIZE`（56KB）。
  - 简化方案（推荐先做）：备份仍按 56KB 全量（BACKUP 区 64KB 够用），但 **`meta.backup_len` 必须记 56KB**。
  - 精确方案：让 APP 在镜像头写入"自身长度 + CRC"，BL 先读镜像头再决定备份长度。
- **`main()`（L114）**：`meta.backup_len = meta.firmware_len;` ← **这就是语义 bug**（把"新固件长度"当成"旧固件备份长度"）。改为记录真实备份长度，并**同时写 `meta.backup_crc32`**（该字段已定义但从未赋值）。
- **`main()`（L128）**：回滚 `Flash_App_From_SPI(SPI_BACKUP_ADDR, meta.backup_len)` 依赖上面修正后的长度。

**验收**：故意发"CRC 正确但首地址非法"的固件，BL 刷完回读发现不符 → 拒绝并回滚，设备仍能正常启动。

## P6 黄金镜像兜底

### 25. `Bootloader/main.c`
- **`main()`（L126）** `boot_retry_cnt >= 3` 分支改为三级降级：
  ```
  if (Golden_Valid())       Flash_App_From_SPI(SPI_GOLDEN_ADDR, golden_len);
  else if (Backup_Valid())  Flash_App_From_SPI(SPI_BACKUP_ADDR, meta.backup_len);
  else                      安全模式（只跑 BL + LCD 报错，不跳 APP）
  ```
- 新增 `static uint8_t Golden_Valid(void)`：校验 `SPI_GOLDEN_ADDR` 处镜像头（magic + len + crc32）。
- 现状：`SPI_GOLDEN_ADDR (0x00020000)` 已定义但**零引用**，属"预留未启用"。

### 26. 新建 `tools/program_golden.py`（产线工装）
- 烧 BL → 烧首版 APP → 把首版 APP 镜像写入 `SPI_GOLDEN_ADDR` 并写 golden 头。
- ⚠️ 这是**产线新增工序**，需写入产线 SOP。

## 建议实施顺序（每步可独立验收）

| 序 | 阶段 | 工作量 | 为什么这个顺序 |
|---|---|---|---|
| 1 | **P0** | 半天 | 不做则现有系统本身就跑不通，后续验证全是空中楼阁 |
| 2 | **P5 的 `backup_len` 一行修正** | 1 小时 | 改 1 行，避免回滚时刷入错误长度导致真变砖 |
| 3 | **P1** | 2~3 天 | 解 4KB 上限，是后续一切的前提 |
| 4 | **P2** | 1 天 | meta 原子性 |
| 5 | **P4** | 1 天 | IWDG + 喂狗任务（BL/APP 需成对做） |
| 6 | **P5 回读校验** | 半天 | 依赖 P1 的镜像头设计 |
| 7 | **P6** | 1 天 + 产线工序 | 依赖 P2/P5 |
| 8 | **P3 验签** | 2~3 天（可选） | 依赖 P3 决策 |

## 一句话总结

A 档改造落点 = **2 个 Keil 工程 + 2 个 Python 工具，约 26 处代码改动点**。
Bootloader 是"最危险也最不该膨胀"的地方（8KB，当前余量约 5KB），因此**验签、大块 CRC 这类重活应放 APP 侧，BL 只做四件事：读 meta → 搬运 → 校验 → 跳转**。
