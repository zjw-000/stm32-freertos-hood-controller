## 2. 关键事实（实测，非推测）

### 2.1 双区内存布局**早已存在**，靠显式 scatter 文件，不是 uvprojx 的 IROM
- `OBJ/APP.sct` → `LR_IROM1 0x08002000 0x0000E000`（APP 56KB）
- `OBJ/Bootloader.sct` → `LR_IROM1 0x08000000 0x00002000`（BL 8KB）
- `project.uvprojx` / `bootloader.uvprojx` 的 `<IROM>0x8000000/0x10000` **只影响 Keil 界面的百分比显示**，
  真正的链接地址由 `LDads` 段里指定的 scatter 文件决定。
- ⚠️ 所以"把 APP 挪到 0x08002000"这件事**不需要改 uvprojx 的 IROM**，改了反而与 .sct 打架。

### 2.2 APP 的 RAM 已经**正好 100% 用满**
基线（改造前，实测）：`Code=37434 RO-data=7506 RW-data=320 ZI-data=20160`
→ Flash = 37434+7506+320 = **45260 B / 57344 B (0xE000)**
→ RAM = 320+20160 = **20480 B / 20480 B (0x5000) = 100%**

**后果：APP 侧新增任何全局变量/静态变量都会直接链接失败。**
必须先回收 RAM：`BSP/IAP/iap.c` 的 `u16 iapbuf[512]`（=1024 B）等。
（`receive_buff` 在 `0x20004000`，是 RAM 顶部的独立 4KB 区，不占 linker 的 ZI 统计，别动它。）

### 2.3 旧 `BootMeta_t`（v1，32 字节，committed 版本）
```
magic(u32) firmware_len(u32) firmware_crc32(u32)
ota_state(u8) boot_retry_cnt(u8) ver_major(u8) ver_minor(u8)
backup_len(u32) backup_crc32(u32) reserved[8]
```
旧分区：`SPI_META_ADDR=0x0`（单份）、`SPI_DOWNLOAD_ADDR=0x1000`、
`SPI_BACKUP_ADDR=0x10000`、`SPI_GOLDEN_ADDR=0x20000`（**定义了但零引用**）。

⚠️ **v2 是硬破坏性变更**：字段名/大小全变，`Bootloader/main.c` 与 `APP_TASK/app_tasks.c`
两处消费者必须**同一步改完**，否则编译必然报 `struct has no field "firmware_len"`。
（踩坑：先改 `boot_config.h` 没同步改消费者 → 两工程同时编译失败。）

### 2.4 两个 Keil 工程**共用**同一份 `USER/system_stm32f10x.c`
→ 不能直接把 `VECT_TAB_OFFSET` 改成 0x2000，否则 Bootloader 也被改坏。
→ 做法：源码里用 `#ifndef VECT_TAB_OFFSET` 包住默认值 0x0；
  只在 APP 工程的 C/C++ Define 里加 `VECT_TAB_OFFSET=0x2000`。

### 2.5 W25QXX 驱动 API 语义（实测源码）
| 函数 | 参数语义 |
|---|---|
| `W25QXX_Erase_Sector(idx)` | **扇区索引**，内部 `idx*4096` |
| `W25QXX_Erase_Range(addr,len)` | **字节地址 + 字节长度** |
| `W25QXX_Read(buf,addr,len)` | 字节地址；`len` 是 **u16**（单次 ≤65535） |
| `W25QXX_Write(buf,addr,len)` | 字节地址；`len` 是 **u16** |

### 2.6 主机侧 gcc 单测可行（本工程已验证）
- 桩：`tools/host_test/stm32f10x.h` 只 `#include <stdint.h>`
- 编译：`gcc -std=c99 -Wall -Wextra -I Shared -I tools/host_test tools/host_test/test_shared.c`
- 结果：**35/35 断言通过**，CRC32 与 `zlib.crc32` 逐位一致，协议帧与 Python 重实现逐字节一致。

## 3. 改造后的设计（已定稿）

### 3.1 分区表
| 区 | 地址 | 大小 |
|---|---|---|
| W25Q64 META A 槽 | `0x000000` | 4 KB |
| W25Q64 META B 槽 | `0x001000` | 4 KB |
| W25Q64 DOWNLOAD | `0x002000` | 56 KB |
| W25Q64 BACKUP | `0x010000` | 64 KB |
| W25Q64 GOLDEN | `0x020000` | 64 KB |

### 3.2 `BootMeta_t` v2（80 字节 = 20 个字）
`magic, version, seq, ota_state, app_size, app_crc32, backup_size, backup_crc32,`
`golden_size, golden_crc32, boot_retry_cnt, max_retry, confirmed, fw_version,`
`reserved[5], meta_crc32`
- `meta_crc32` 保护前 19 个字（76 字节）
- 有效性 = magic + version + meta_crc32 + ota_state 范围 四重校验
- A/B 双槽选 `seq` 大者；写入永远写"较旧/无效"的那一槽

### 3.3 协议 v2
`A5 5A | type | seq(u16) | len(u16) | payload | crc32(u32)`
- crc32 覆盖 `[type .. payload 末字节]`，与 `zlib.crc32` 一致
- `CMD_BEGIN=1`(payload: size u32+crc32 u32+ver u32+hmac[32]) / `DATA=2`(payload: offset u32+data) / `END=3` / `ABORT=4` / `BURN_GOLDEN=5`
- `ACK=0x81` / `NAK=0x82`
- 分片 1024 B/帧，**逐帧 ACK（stop-and-wait）**，防 DMA 缓冲溢出

## 5. 踩坑记录

1. **别用 `printf("...%u", F(&x), x.seq)`**：函数有副作用又读其结果，C 参数求值顺序未定义
   （gcc 从右往左求值）→ 读到调用前的旧值，制造"逻辑写错"的假阳性。必须拆成独立语句。
2. **改共享头文件前先 `git show HEAD:<file>` 看原始版本**：本工程的 `Shared/boot_config.h`
   是已提交文件，直接覆盖会让两个工程同时编译失败，且丢失旧字段名信息。
3. **`docs/plans/` 在 `code/docs/plans/` 下**，不在项目根目录（根目录只有 `文档/`）。
4. `file_read` 的行号分隔符不属于文件内容。

### 6.3 本轮新踩的坑
5. **BL 工程的文件组里没有 `stm32f10x_iwdg.c`**：`USER/stm32f10x_conf.h` 里 `#include "stm32f10x_iwdg.h"` 让原型可见，
   所以编译期不报错，只在**链接期**报 `L6218E: Undefined symbol IWDG_Enable`（5 个）。
   → 极简 BL 的正确解法是**直接写 IWDG 寄存器**（`IWDG->KR/PR/RLR`），既不用改工程文件，又省下整个驱动的 Flash。
6. **`at(0x20004000)` 的 `receive_buff` 不占 linker ZI 统计**，但它占真实 RAM：
   `buff_size` 从 4096 降到 2048 后，RAM 统计只降了约 1.7KB（另有其它变化），真实可用 RAM 变大。
7. **`Bootloader/main.c` 与 APP 共用 `Shared/*.h`，但 BL 工程**不能**直接链接 `BSP/CRC32/crc32.c`**
   （查表版要 1KB RO 表，对 8KB BL 太贵）→ 统一用 `Shared/boot_crc.h` 的逐位版。
8. `Shared/boot_config.h` 里 `IAP_BEGIN_PAYLOAD_LEN` 曾写成 40，但 `4+4+4+32=44`。
   **定常量时必须回算一遍**，否则上位机与下位机对 payload 长度判断不一致，BEGIN 帧永远被 NAK。

### 7.4 本轮新踩的坑

9. **`parse_frames` 必须处理"长度字段越界"**：垃圾字节流里若恰好出现 `A5 5A`，后面的
   `len` 可能是 0xFFxx，解析器会一直"等更多数据"而卡死。C 端与 Python 端都按
   "长度 > MAX_FRAME_LEN 即视为非法帧、丢 1 字节重同步"处理，两端行为必须一致。
10. **假串口模型的 `in_waiting` 语义**：模型里 `tx` 是 `bytearray`，`read(n)` 后要
    `del tx[:n]`；否则重传场景下设备会反复"收到"同一批数据，制造假阳性。
11. **离线自测的设备模型是"人工照抄 APP 源码"**，不是链接真固件：APP 侧逻辑一改，
    这个模型必须同步改，否则自测通过但真机失败。已在模型里逐段标注对应的 C 函数名。
